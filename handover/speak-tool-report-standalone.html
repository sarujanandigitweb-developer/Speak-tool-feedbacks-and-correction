Analysis & upgrade proposal

Speak Tool Teardown

The voice packing tool works. The problem is that its bug list keeps regenerating — 160 reports over five months, 63 still outstanding, and the same defects filed up to five times across six stations. Here is why, and what to do about it.

For Varmen Scope 6 stations · 160 feedback items · 1,465 lines of Apps Script Date 13 Aug 2026
Part one

What the tool actually is

A Google Apps Script add-on bound to a spreadsheet. It turns the day's order list into a hands-free audio pick-and-pack stream. Instead of reading a printed packlist and looking up and down between paper and shelf, the packer hears the order — quantity, product, then postcode — and says “next” to advance. Eyes and hands stay on the stock.

The one thing to understand: every product has two names

The tool never reads the marketplace title aloud. Titles are 40-word SEO text — unpronounceable and useless to a packer. Each product carries a second, phonetic name written for the ear, pulled from a shared Names Master Sheet owned by the postage team. 

Title  → LEDSone Pack 6 | Vintage LED Dimmable B22 Light Bulb, ST64 8W
         (Equivalent 60W) 2700K Warm White 806 Lumens Amber Glass | ...

Name   → S T 6 4 b22 8 wats

Spoken → :: S T 6 4 b22 8 wats :: 6: :Post Code: W 3 6 H H

This is why most “it said the wrong thing” reports are data fixes, not code fixes. The exception is postcodes and numeric codes — those are unbounded, so no dictionary can ever cover them. That distinction turns out to explain the single largest cluster of open bugs.

The data moves through two tabs. Sheet1 is the raw import from Amazon UK/DE/FR/IE, eBay, Wayfair, B&Q and Shopify — one row per line item. A cleaning script projects it into Cleaned Data, the speech-ready queue.

Selling platforms → Sheet1 169 rows · 17 cols │ cleaning script ──────┤ phonetic name lookup · postcode extraction · combo numbering ▼ Cleaned Data 140 rows · 18 cols │ Apps Script builds the utterance ▼ Browser Web Speech API ├─ SpeechSynthesis → speaks it └─ SpeechRecognition → listens for "next" / "back" / "stop" ▼ Packer

Five order types the business defined

#TypeWhat it means
1Single order, single productOne customer, one SKU
2Merge order, single productsSeveral orders to the same address — one parcel
3Single order, multi productsA combo: one listing, several component SKUs

Types 2–5 generate about a third of all feedback. The packer must hear the whole parcel — “component 1 of 3… component 2 of 3…” with the postcode last — or they under-pack.

Themes C, A and B alone account for 41 of the 63. And they recur because of three structural causes that no individual ticket describes.

Cause 1

Speech is built as a plain string

13 items

There is no SSML anywhere in the codebase. The utterance is concatenated and handed to the browser, which applies English number rules to any digit run. IP20 becomes “twenty thousand”. PE11 3TY becomes “P E eleven three T Y”. German 00049 loses its leading zeros entirely.

Every fix so far has been to patch one product name at a time in the Names Master Sheet. That works for names. It cannot work for postcodes — there is a new one every order. It needs a rule, not a lookup. The developer's own note on the very first ticket says exactly this: “i can't do for single one, can do it for every think.” He was right.

Cause 2

Merge orders exist in the warehouse but not in the data

20 items

The Merge Order column is populated on 6 of 140 rows. The tool has almost nothing to group by, so it falls back to matching postcodes — which fails in both directions: two different customers at one postcode get falsely merged, and one customer whose orders carry different postcodes never gets merged at all.

This has been closed as “not possible” four times, and the Schmutter tab escalated it with “We need to find a way by MD.” It is possible. It is not possible while the script iterates a flat list of rows — which is a data-model problem, not a speech problem.

Cause 3

Six stations run six independent copies of the script

drives the repeats

A fix is six deployments, done by hand. Four Schmutter and Kronen items are word-for-word identical. The same postcode bug is filed five times. One ticket simply reads “everything changed in Unit 4 must also be changed in Unit 3.”

Nobody knows which copy is current, because the script has never been in version control.

Part three

What the code proved

All 1,465 lines read. Every cause above is confirmed at line level — and five defects turned up that nobody has ever filed, because no packer could see them.

C1

The tab is written twice, and the tool depends on the leftovers

Unreported

Cleaned Data is written by two functions with different column counts. The first writes 18 columns; the second overwrites only the first 15. Columns 16, 17 and 18 survive untouched — which is exactly what the live sheet shows, and why it has duplicate headers. 

Merge SKU.gs:58  writes 18 cols  →  [ …Sheet1 headers…, "SKU Combined" ]
cleaned.gs:153   writes 15 cols  →  overwrites A–O only

result:  P = Component  (leftover)
         Q = Send Order Instruction  (leftover)
         R = SKU Combined  (leftover — and never rebuilt)

A later step then deletes rows and rewrites A–O. Column R does not shift with them, so it is now misaligned with its own rows. And the speak tool groups orders by that column, in preference to Combo SKU: 

Lithursan.gs:64
const groupKey = skuCombined !== "" ? skuCombined : comboSku;

Order grouping runs off a stale, row-shifted column. This is the best explanation yet for combos that group correctly one day and not the next — and it may be sitting underneath several Theme C reports. Fix this before the merge-order rework, not after.

Likely underneath FB-075 · FB-079 · and part of Theme C
C2

Two ticket threads are the same bug

Unreported

One function blanks a postcode whenever it matches the row above — adjacency only, with no customer check. That is the “same postcode” complaint. The next function then clears column F wherever the postcode is empty — and column F is Instruction QR. 

cleaned.gs:167  if (current === previous) valuesD[i-1][0] = '';   // postcode gone
cleaned.gs:190  if (!valuesD[i][0]) valuesF[i][0] = '';           // QR gone too

Deleting a postcode silently deletes that order's QR instruction. Two teams have been filing two separate threads against one root cause for months. It also explains the measured fill rates: Post Code 109/140, Instruction QR 5/140.

FB-071 · FB-116 ⟷ FB-060 · FB-070 · FB-078
C3

Four items marked “Done” were never built

Unreported

The quantity-based pause is computed, passed to the browser, and never read. The hold feature has an array, CSS and render logic — but nothing ever puts anything into it, and there is no Hold button. html2canvas is loaded from a CDN and never called. And the pause button calls synth.pause() — while synth.resume() appears nowhere in the codebase, so pause is one-way.

All four are marked True in the feedback sheet. This is the clearest possible argument for adding a verification step: right now “Done” carries no information.

FB-009 hold · FB-012 pause · FB-014 quantity pause · FB-021 screenshot
C4

The tool triggers its own voice commands

Unreported

Nothing pauses speech recognition while the tool is speaking. The microphone stays open, the tool says “Post Code” out loud, the mic hears it, and the handler matches on includes("post code") — firing the postcode command at itself.

Separately, recognition is stopped and restarted on the same line, which throws — and the error handler does not restart it. Recognition can die permanently mid-session, with no indication to the packer. That is the ticket that reads “Next command is not listening enough — getting tired from it.”

FB-046 · FB-047 · FB-055 · FB-132 · FB-133
C5

A two-character bug silences whole orders

Unreported

The SKU lookup strips three characters to remove a "PK" suffix that is two characters long. It works by luck for single-digit packs and breaks for everything else. And the line immediately after blanks the quantity whenever the name lookup fails. 

cleaned.gs:112  rawSku.slice(0, -3)   // "…10PK" → "…1"  ✗
cleaned.gs:116  if (!name) quantity = '';   // miss → row says nothing at all

One line, two ticket threads, and it accounts for the blank cells measured in the data (6 blank names, 6 blank quantities).

FB-054 · FB-072 · FB-150

One correction worth flagging

Before reading the code I recommended checking whether the Names Master Sheet actually propagates to the stations — the worry being that months of pronunciation fixes had silently never landed. The code answers it: the sheet is read live on every run. Nothing was lost that way. The real fault is the SKU lookup bug in C5, one line below it.

How the merge order should sound

Postcode last and said once. Quantity before the name. Pack sequence ordered — bulb first, shade last. “Merge order” said once, then components enumerated. 

"Merge order. Three components."
"Component one of three. Two.
 Forty centimetre hemp shade."
"Component two of three. One.
 One metre short holder pendant full set."
"Component three of three. One.
 Reducer plate white."
"Instruction QR available."
"Post code. C M — six. Three — Z — B."

Fix the feedback loop itself

The Ref column exists on every station tab and is empty on all 160 rows. Nothing has an ID, so nothing can be closed and nobody can tell a repeat from a new report.

Replace True/False with Open · In progress · Fixed · Won't fix · Blocked upstream — “False” currently means both not done yet and refused, which is exactly why items keep coming back. Record which station and script version a fix landed in, and verify before closing.

Every item now has an ID in the register — paste them back into Ref.

Part five

Decisions I need from you

  1. Customer note — speak it, or just show it?

    Unit 4 wants it displayed but not spoken. Unit 3 Lampshade wants it spoken. Direct conflict — pick one, or I build it as a per-station setting.

  2. Can the platform import add a Shipping Service column?

    Four items — next-day sticker, Evri/Royal Mail, “S label 2 kilos” — are blocked without it. The developer's note “not found in the packlist” is correct: the data doesn't exist. Someone needs to own this.

  3. Approve consolidating six script copies into one shared library?

    It changes how deployments work across all six stations. I won't start without sign-off.

  4. Budget for USB foot pedals — roughly £15 × 6?

    The most reliable fix for “getting tired from it”. Hands stay free, and it works when the wifi doesn't.

  5. Who owns the combo→image mapping on the dashboard?

    Three items need a reconciliation pass against it and I don't know whose system it is.
