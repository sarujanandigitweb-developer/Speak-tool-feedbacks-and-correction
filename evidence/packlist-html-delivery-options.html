Speak Tool Without the Spreadsheet

The pack list already opens as an HTML page. If the Speak Tool were a browser extension — or something else — what could it actually do, and what would break?

Author Sarujanan Date 17 Aug 2026 For Varmen Status Analysis only — nothing built
Summary What it has What it lacks Options Comparison Recommendation Blockers Credentials

Summary

The question has already been half-answered, in this repository

The pack list HTML already contains most of what the Speak Tool needs. I confirmed this against 17 real pack list files saved under speak_tool/uploads/, and against an existing Flask prototype — speak_tool/app.py, dated July 2025 — that already scrapes those files into the exact Sheet1 layout we use today.

That changes what we are deciding. This is not “can we read the pack list without Excel”: that is proven, and already written. The real question is where the things the pack list does not contain would live — because those are what the spreadsheet is actually providing.

Can a browser extension read the pack list? Yes — every field is in the DOM
Can it speak, show images, take voice commands? Yes — fewer limits than today
Can it replace the spreadsheet outright? Not as-is — six things have no home
Recommended path Option C now, Option D as the destination

Found in the prototype — worth taking regardless

app.py carries a pack-code map our Apps Script does not have: 2PK–9PK = 2–9, APK = 10, CPK = 20, DPK = 30, EPK = 50, FPK = 100, NPK = 200, PPK = 300, QPK = 500, RPK = 1000.

This resolves a limitation I documented in ppProductSize(), where LSFT2205PK is ambiguous between “220 + 5-pack” and “2205 + pack”. With this map the ambiguity goes away — useful whichever option is chosen.

Options

Five ways to deliver this

A

Browser extension in the live dashboard page

A content script adds a Speak button straight into the pack list.

Does well

  • No export step at all. Open, save, upload, wait, Clean and Merge — that whole chain disappears.
  • Escapes every Apps Script limit: the 6-minute cap, the modal that hangs from the editor, the 1600 px width ceiling.
  • Can cache the names master and SOT locally, so lookups survive a slow network.
  • Can hold real state — pick progress, collection pool, per-component ticks — which one-shot injection cannot.

Costs

  • The three typed fields have no home unless the extension builds its own input UI.
  • Needs Google auth inside the browser to reach the names master and SOT.
  • Bound to someone else’s CSS classes. A styling change on the dashboard silently breaks picking.
  • Install, policy and updates across six stations become an IT task.
B

Bookmarklet or userscript

The same idea without the packaging — the packer clicks a bookmark on the page.

Does well

  • Cheapest to deploy and update — no store, no policy, no per-machine install.
  • A realistic way to prove Option A before committing to it.

Costs

  • Same DOM fragility as Option A.
  • Tighter limits on storage and cross-origin calls, so caching the names master and SOT is harder.
C

Standalone page, pack list dropped into it

What app.py already half-does — but speaking directly instead of writing to a sheet.

Recommended

Does well

  • The parser already exists and already works. Shortest path from where we are.
  • Independent of the dashboard’s release cycle — if their DOM changes, one parser is fixed in one place and picking keeps running meanwhile.
  • Hosts the three typed fields as real inputs, and can persist them.
  • Holds the names master and SOT server-side, so no browser auth work.
  • One place to fix — the six-station drift stops recurring.

Costs

  • One step remains for the packer: save or paste the pack list.
  • That step already exists today, and this removes the spreadsheet, Clean and Merge, and Apps Script entirely.
D

Ask the dashboard team to add the Speak view

Built into the pack list page itself.

Destination

Does well

  • The correct long-term answer: no scraping, no DOM coupling, no export.
  • The three typed fields become real fields with real validation.

Costs

  • Depends entirely on another team’s roadmap, so we cannot schedule it.
E

Keep the current spreadsheet flow

Everything works, and this week’s nine fixes are tested and ready.

Does well

  • No new work, no new risk, no migration.

Costs

  • Keeps what we already measured: manual export, six forked script copies, hand-typed operational fields.
  • Keeps an editor ▶ Run button that destroyed 60 SKUs in Sheet1.

Recommendation

Start with C, treat D as the destination

Option C is the shortest honest path. The parser is already written and already correct. Redirecting it from “write to a spreadsheet” to “speak directly” removes the spreadsheet, the Apps Script, the Clean and Merge run and the six forked copies in one move — and it gives the three typed fields a real home instead of a free-text column.

Option B is worth one day if we want to feel the extension experience on the live page before committing to Option A.

Option A only after the DOM contract is agreed with the dashboard team. Building an extension on undocumented CSS classes recreates exactly the fragility we have spent this week removing.

Option D should be raised with them now, because everything in A–C is a workaround for the pack list not offering this itself.

Whichever is chosen, the packing logic does not need rewriting. Classification, the conditional priority, the just-in-time collection and the speech segmentation are plain rules — they move across unchanged.

Before any build starts

Six questions that block the work

#QuestionWhy it blocks
1Where do Instruction QR, Send Order Instruction and Status get entered? 46 of 169 rows carry one; they are operational instructions, not decoration
2Is the pack list DOM stable, and will we be told before it changes? Every option except D depends on it
3Can the names master and SOT be exposed as an API or scheduled export? Otherwise every option needs Google auth in the browser
4Does the pack list carry a real order ID? We use the postcode as the order key because Sheet1 has none — and two customers can share a postcode
5Do the stations have reliable network? Recognition is cloud-backed; synthesis is local. Voice commands fail offline, buttons do not
6One shared tool for all six stations, or per-station config? The six-copy fork is the root cause of recurring defects

Related finding

Credential handling

speak_tool/service-account-file.json is a live Google service-account private key (unit4-337@coherent-surf-461012-f8.iam.gserviceaccount.com). It is correctly excluded from git by .gitignore — I verified this. Two points regardless:

  • app.py hardcodes a Windows path for it, so the key is expected to sit on a developer machine. Any move to a shared service should put it in a secret store, not on disk beside the code.
  • The key grants spreadsheet write access. This week’s SKU loss was caused by a function run by hand from the Apps Script editor, not by this key — but both are the same category: write access to live data with no guard in front of it.
